## Findings

### 1. P2 — A failed index request disables both interactive tools until reload

- Evidence: `src/scripts/corpus.ts:22` caches the request promise, including rejection, and never resets it. `src/pages/explore/phrases.astro:69` and `src/pages/research/compare.astro:88` await it without error handling; the phrase focus preload at `phrases.astro:62` is also unhandled.
- Reproduce: block `/search-index.json` or go offline before first opening comparison / focusing the phrase input; submit a phrase; restore networking and try again on the same page.
- Impact: the tool remains at «جارٍ البناء…» / «جارٍ التحميل…», emits an unhandled rejection, and cannot recover with the visible controls. On phrases, an unsuccessful focus preload already poisons later submissions.
- Minimum fix: reset the cached promise after failure; catch at each tool boundary and present an Arabic failure message plus retry. Hide stale results while a new computation is pending or fails.
- Confidence: source-confirmed failure path; blocked-request browser check pending.

### 2. P2 — Invalid shared comparison URLs crash instead of recovering

- Evidence: `src/pages/research/compare.astro:72` assigns URL IDs without validating against options; `compare.astro:90` can produce index `-1`; `compare.astro:101` unconditionally reads `verses[0].text`.
- Reproduce: open `/research/compare/?a=missing&b=r1-002` (also test `?a=&b=r1-002`). The invalid value leaves the first select empty, and no verses exist for index `-1`.
- Impact: comparison stays blank with no explanation; a mistyped or obsolete shared link becomes a broken page experience.
- Minimum fix: validate both IDs before assigning selects, use valid defaults or an inline invalid-selection message, and guard empty verse lists before rendering. Preserve the route and parameter names.
- Confidence: source-confirmed failure path; browser confirmation pending.

### 3. P2 — Split words become false standalone words in phrase/comparison analysis

- Evidence: `src/scripts/corpus.ts:31` replaces the hemistich separator with a space, and `corpus.ts:33`–`36` turns each resulting fragment into an independent normalized token. The project's content rule explicitly identifies tatweel before `#` as one word split across halves.
- Current edition example (fresh read): `r1-008`, verse 4 contains «بالخيـ # ف». Verse 7 similarly contains «الوجـ # د».
- Reproduce: search the phrase tree for «بالخي». Its sequence includes «ف» as the next word in that verse; searching «بالخيف» cannot find the complete word there. Compare a poem with such verses and inspect the derived frequent-word list: longer fragments can be counted as words too (`compare.astro:79`).
- Impact: the linguistic tools teach/expose artificial words and miss the real word at an explicitly documented edition boundary.
- Minimum fix: join only the derived analysis token across a marked split, with a mapping back to untouched verse halves for display/highlighting. Never rewrite the edition or displayed poem text.
- Confidence: source-confirmed tokenization defect, grounded in current edition examples; browser confirmation pending.

### 4. P2 — Phrase tree silently makes most branches and examples unreachable

- Evidence: `src/pages/explore/phrases.astro:124` limits each branch to 14 alternatives; `phrases.astro:102` limits examples to 30. No remaining-count label, expansion control, pagination or link to the rest exists in the page.
- Fresh source-data inspection using the same fold/token approach: «الدهر» occurs in 269 verses, with 210 distinct preceding tokens and 193 following tokens. The UI can expose only the first 14 choices in each direction and first 30 verses.
- Reproduce: submit «الدهر», count branch buttons and examples, then try to inspect any less frequent continuation from the tree.
- Impact: readers cannot discover most continuations, although the page invites them to build a phrase word by word and reports the full verse total. The limitation can look like complete coverage.
- Minimum fix: label the visible/total counts and add lightweight «عرض المزيد» controls for branch alternatives and verse samples. Preserve the current compact initial rendering.
- Confidence: source-confirmed hard limits and missing access; browser confirmation pending.

### 5. P2 — Phrase expansion removes the keyboard user's focused control

- Evidence: `src/pages/explore/phrases.astro:133` calls `build()` from a branch button; rebuilding calls `renderBranch()` for both sides (`phrases.astro:97`–`98`), whose `replaceChildren()` at `phrases.astro:125` removes every existing branch button. No focus restoration follows.
- Reproduce: submit a phrase, Tab to a continuation button and activate it with Enter/Space; then press Tab again and inspect active focus and its next destination.
- Impact: the active control is detached after each expansion, so a keyboard reader can lose their place and traverse the page again to continue a multiword exploration. Live status text does not restore focus.
- Minimum fix: restore focus to a stable phrase heading or deliberately chosen replacement control after rebuilding, with a short result announcement. Keep ordinary text-entry submission behavior predictable.
- Confidence: source-confirmed focus-removal path; exact browser focus fallback still needs confirmation.

### 6. P3 — Clearing the phrase does not reset the previous analysis

- Evidence: `src/pages/explore/phrases.astro:66` returns for an empty normalized query before clearing the tree, examples, status or `?q=`. No input/search/reset handler exists.
- Reproduce: submit «الدهر», clear the search input (including its native clear button), submit again, then copy/reload the URL.
- Impact: empty input continues to display the old tree and share the old phrase, making the tool's current state ambiguous.
- Minimum fix: handle an empty query by clearing/hiding derived results, restoring the initial prompt and deleting `q`; support the native search-clear event too. Optionally provide a small explicit reset action.
- Confidence: source-confirmed behavior; browser confirmation pending.

### 7. P3 — Rhyme-wheel selection lands at a closed list

- Evidence: `src/pages/explore/rhymes.astro:44` and `:64` link to qafiya fragments, while the destination `src/components/IndexGroups.astro:25` creates closed `<details>`. `src/pages/explore/qafiya.astro` has no fragment-opening script. The fragment points to the wrapping list item, not a descendant inside the hidden content.
- Reproduce: choose a wheel sector/legend letter, such as ب; observe `/explore/qafiya/#ب`; inspect whether the corresponding poems are visible without expanding the group.
- Impact: the instruction «اختر قطاعًا لتنتقل إلى قصائده» leads to a collapsed header and another unexplained action. This is especially disorienting when arriving from the visual wheel.
- Minimum fix: open the targeted group on initial load/hash change, as the relations page already does, or link directly to the existing filtered `/diwan/?rhyme=…` listing.
- Confidence: source-confirmed closed target; browser confirmation pending.

### 8. P3 — Relations hide their disclosure affordance and leave chip counts unexplained

- Evidence: `src/pages/explore/relations.astro:47` renders just a term and poem count in each summary; `relations.astro:128`–`132` suppresses the native disclosure marker without replacement. Related chips output `r.shared` at `:56` and `:58`, with no local unit/explanation.
- Reproduce: open `/explore/relations/` as a first-time reader; determine which entries expand, then open one and interpret the small number next to each related word.
- Impact: a term card can read as a static statistic; related counts can be mistaken for occurrence counts rather than shared-poem counts. This is a discoverability/terminology issue, not a claim that native details lacks keyboard semantics.
- Minimum fix: add a small disclosure chevron that reflects `open`, and explain the chip numbers once («عدد القصائد المشتركة»), ideally in each chip's accessible name too.
- Confidence: source-confirmed missing affordance/explanation; visual impact needs browser validation.

## Conditional risks to verify in the browser

1. **Atlas mobile selection overlap:** `src/components/AtlasMap.astro:66` supplies invisible circular hit areas; at `:152`–`156` they grow to radius 60 SVG units. Later painted links win overlaps; the component explicitly paints more-cited places above others (`:60`–`64`). At ~375px, tap dense place clusters and compare the opened profile to the intended visible name/dot. Do not classify this as a confirmed wrong-destination defect until tested. Minimum remedy if reproduced: avoid full-circle overlapping hit regions or offer a local disambiguation; keep the complete place list as fallback.
2. **Atlas label readability:** 15-unit labels (`AtlasMap.astro:133`) shrink with the entire 900-unit map and are not independently scaled for mobile. Inspect phone screenshots in both themes, including dense clusters, and test browser zoom. Do not claim unreadability from source alone. A larger accessible map view or clear cue to use the list may suffice.
3. **Long phrase width:** `phrases.astro:191` uses a desktop `1fr auto 1fr` grid; the center phrase has no max-width/overflow wrapping. Explore a long phrase near 761px and desktop with large text to check horizontal overflow. Mobile switches to one column at `:286`, but long unbroken terms still need checking.
4. **Comparison poem selection:** each native select has all 685 options, labeled with title/meter/rhyme only (`compare.astro:33`), and phone CSS stacks the selectors. Test finding a known poem using the actual phone picker; verify title duplication/truncation before calling it a defect. If slow, add a lightweight text filter or an existing poem-page “compare” entry point.
5. **Rhyme-wheel touch targets:** small sectors are proportional to poem count; sectors below the threshold receive no visible letter (`rhymes.astro:25`). Test selecting rare letters at phone width. The full linked legend is a good fallback; avoid inflating this into a blocker without checking it.
