# Core pages and shared shell: source audit, 2026-10-24

Scope: home, poem catalogue, search, saved poems, 404, shared shell/navigation/styles and relevant browser helpers. Read AGENTS.md and PROGRESS.md first. This is an independent inspection of the current source; earlier audit reports were not used as evidence. No implementation, content or data changes.

**Evidence boundary:** all findings below are source-derived. The described state transitions follow the code, but screenshots, actual touch use, screen-reader behavior, iOS behavior and visual wrapping still require the lead's browser pass. P1 means a primary task cannot complete in the stated conditions; P2 means substantial confusion or access friction; P3 means smaller polish or discoverability problems. No claim of measured contrast failure or measured overflow is made.

## Findings

### C01 — P1: failed search downloads have no recovery state

- Evidence: `src/pages/search.astro:121–138` caches download promises with `??=`; `:177–214` awaits them without `try/catch`; `:142` also starts a promise without a rejection handler. Neither fetch checks `response.ok`.
- Reproduce: open search with cache disabled; block `/search-index.json` (or select notes and block `/search-notes.json`); search for `الزمان`; unblock and search again.
- Impact: the page remains at «جارٍ البحث…», without explanation or retry. A rejected cached promise fails every later search in the same visit. Focus-triggered preloading can also cause an unhandled rejection before submission.
- Minimal fix: check HTTP success, catch failures, reset the failed promise, show a useful Arabic error and a retry action, and clear stale result/loading state. Handle prefetch rejection too.
- Lead test: offline → online recovery for both indexes, 500/invalid JSON responses, and no console rejection. Confirm input/filter values survive retry.

### C02 — P2: clearing a search can repopulate results for the erased query

- Evidence: `src/pages/search.astro:177–195`: the empty-query return precedes `++runId`, so clearing never invalidates an earlier in-flight run.
- Reproduce: throttle the first index download; submit `الزمان`; clear the input before the download completes; wait for it.
- Impact: the input and URL are empty but old results and their count return. Examples may remain visible alongside those results.
- Minimal fix: advance the run token at the beginning of every run, before the empty-query branch; cancel any queued typing run on explicit submit.
- Lead test: repeat during main-index and notes-index downloads; clear using the native search-field X as well as keyboard deletion.

### C03 — P2: previous search results remain actionable during a new search

- Evidence: `src/pages/search.astro:190–207` changes only the status before awaiting downloads; results are cleared only afterward. `:216–227` reads the *current* field when rendering additional entries, and `:272` leaves “more” active.
- Reproduce: search a frequent word, then choose «الحواشي والشروح» with a throttled first notes download. While it says «جارٍ البحث…», activate «عرض المزيد».
- Impact: old verse matches append with note formatting while controls claim the notes field is active. Even without clicking, old results appear to belong to the new query/filter until loading completes.
- Minimal fix: clear or explicitly mark old results stale and disable “more” during a run; store the completed search's field with its matches rather than reading live form state in `renderMore()`.
- Lead test: change query and field quickly under throttling; no result should be presented as belonging to a state it was not computed from.

### C04 — P2: auto-hidden phone navigation can retain invisible keyboard focus

- Evidence: `src/layouts/Base.astro:185–198` hides bars after downward scrolling on every page; `src/styles/global.css:504–510` moves them off-screen with transforms. They remain focusable, and no focus-within override restores them.
- Reproduce: at 375px on the long catalogue or search results, scroll down past 240px, then use keyboard/assistive switch navigation into the bottom navigation or top actions without scrolling upward.
- Impact: the focused navigation control may be outside the viewport. Touch users also lose the main route controls while browsing long result lists and must discover that upward movement restores them.
- Minimal fix: show bars whenever they contain focus; consider limiting the reading-specific hide behavior to poem reading, where its purpose is clearest. Preserve existing shell and motion preference support.
- Lead test: keyboard Tab/Shift+Tab after downward scrolling, touch at the end of the list, and light/dark screenshots showing where focus lands.

### C05 — P2: removing a saved item destroys the focused control and rebuilds the entire list

- Evidence: `src/pages/saved.astro:52–74`: remove saves, toasts and calls `render()`, which immediately `replaceChildren()`s every card. No focus restoration or undo exists.
- Reproduce: save three poems, keyboard-focus the middle remove button and activate it; press Tab again. Also remove the last saved item.
- Impact: keyboard/screen-reader users lose their position after each removal; accidental touch removal has no immediate undo and requires finding the poem again. The toast announces removal but cannot restore it.
- Minimal fix: move focus to the adjacent remaining card/removal button, or to the empty-state action when the list empties. Add a short-lived undo action if feasible, without a confirmation modal for every removal.
- Lead test: remove first/middle/last items with keyboard and touch; verify useful focus, sensible announcement and recovery.

### C06 — P2: storage write failures produce success messages while saved state does not change

- Evidence: `src/scripts/shared.ts:12–17` silently swallows persistence failures; `src/pages/saved.astro:64–70` unconditionally announces removal and rerenders from storage afterward.
- Reproduce: with saved poems present, make `localStorage.setItem` throw (browser storage policy/devtools injection), then remove one.
- Impact: «أُزيلت…» appears, yet the card remains because the old stored array is read back. The page promises device storage without explaining that saving is currently unavailable.
- Minimal fix: return a success/failure result from the storage helper and show an Arabic failure notice, or keep a clearly described in-memory state for the visit. Never announce persistence success after a failed write.
- Lead test: blocked storage and quota failure, including the poem-page save control reviewed by the reader reviewer.

### C07 — P2: the home heading splits the poet's name by explicit markup

- Evidence: `src/pages/index.astro:55` renders `ديوان الشريف<br />الرضي`; `:211–215` uses up to 102px type, while `:176–180` reserves only the first column of a two-column hero above 800px. `:436–442` still keeps the hard break at phone sizes.
- Reproduce: view home at 375px, 810px, 1024px and wide desktop with the original font, then with friends' heading-font selections.
- Impact: «الشريف الرضي» cannot stay together even where it would fit; near intermediate widths the first line may also wrap naturally before the forced break, making a three-line title. The latter is a visual hypothesis requiring screenshots.
- Minimal fix: make the intended lines «ديوان» and «الشريف الرضي», grouping the name and choosing a responsive heading size against the actual hero column width. Preserve the existing hero treatment and font choices.
- Lead test: no orphaned «الرضي», clipping, overflow or excessive first-screen height at 320/375/810/1024px, both themes, default and font-lab selections. Do not change poetry text.

### C08 — P2: mobile catalogue search field is below iOS's usual no-zoom size

- Evidence: `src/pages/diwan.astro:249–256` sets the input font to 15px; the phone rules `:359–395` never raise it. Home and full search use larger inputs.
- Reproduce: on actual iPhone Safari, open `/diwan/` and focus «عنوان أو مطلع…».
- Impact: likely automatic page zoom and a less stable keyboard/filter layout. This is a platform-specific hypothesis, not verified in a desktop emulation screenshot.
- Minimal fix: use at least 16px for the mobile input; retain compact surrounding metadata.
- Lead test: actual iOS focus/blur and return from keyboard, including whether fixed bottom navigation overlaps keyboard space.

### C09 — P3: active filters have no quick reset while results still exist

- Evidence: catalogue reset exists only in `#noMatch` (`src/pages/diwan.astro:47–50`, hidden when `shown > 0` at `:151`). Search's no-result message suggests removing restrictions but provides no reset (`src/pages/search.astro:211–213`). Collapsed mobile summaries show only an active count (`search :171–174`, catalogue `:144–145`).
- Reproduce: select several restrictions, collapse options on phone, then search another term that returns few or no results.
- Impact: a reader can forget which restrictions remain and must reopen and individually reset every select/radio. A count alone does not explain that, for example, only notes or volume two is being searched.
- Minimal fix: show a compact active-filter summary and one «إزالة القيود» action whenever non-default filters apply, keeping query text. Reuse existing styling rather than adding another filter system.
- Lead test: restricted shared URLs, empty and non-empty result states, and resetting filters without erasing the query unexpectedly.

### C10 — P3: theme action does not describe the current state or next action

- Evidence: `src/layouts/Base.astro:145–148` always labels the button «تبديل الوضع الليلي» with title «الوضع الليلي»; its handler `:170–174` changes only dataset/storage. Dark mode visually changes the icon (`src/styles/global.css:341–347`) without updating the name/state.
- Reproduce: load with system dark mode or toggle to dark, then inspect/access the theme button with a screen reader.
- Impact: the button still calls itself night mode when activating it would switch to light; no programmatic selected state is supplied.
- Minimal fix: dynamically label the next action («الوضع النهاري»/«الوضع الليلي»), or expose a stable toggle label plus `aria-pressed`, initialized from the effective theme.
- Lead test: saved light/dark, system default, keyboard activation and an accessible-name check after every toggle.

### C11 — P3: shared-URL catalogue filters silently stop working without JavaScript

- Evidence: `src/pages/diwan.astro:17–41` renders functional-looking controls, but all filtering and URL restoration live in the script (`:124–172`); unlike search (`search.astro:85`), catalogue has no noscript explanation. Form has neither an explicit action nor a submit control.
- Reproduce: disable JavaScript and open `/diwan/?meter=الطويل`; inspect the displayed list, then type in the title field or select a volume.
- Impact: the full list displays under a URL that appears restricted, and controls offer no feedback that filtering is unavailable. Reading the full catalogue still works.
- Minimal fix: provide a concise noscript notice that the full list is shown and client filters require JavaScript; hide or disable unavailable filter controls in that state.
- Lead test: JS disabled and a client-bundle load failure, checking that static poem links remain accessible.

## Additional visual checks, not yet established defects

- Catalogue jumps: `src/pages/diwan.astro:115–116`, `:320–323` combines smooth scrolling, focus and content-visibility estimates. Jump to a late rhyme on a cold long page and confirm the focused card lands visibly at the intended spot without substantial layout movement.
- Catalogue mobile rows intentionally ellipsize both titles and opening halves (`:371–388`) and hide the second half/source volume (`:380`). Check long and duplicate titles: readers should still be able to distinguish the destination from the remaining opening text. Do not expand all 685 rows merely to remove truncation.
- Mobile saved removal uses `padding: 6px 10px` and 13px text (`src/pages/saved.astro:119–122`), with no minimum target height. Measure its actual hit box; recommend 44px if it falls short. Catalogue no-match reset (`diwan :279–286`) likewise has zero added padding. These are not claimed WCAG failures without spacing/geometry measurement.
- Home search can fall below the first phone viewport when the hero title or actions wrap (`index.astro:52–74`, `:431–456`). Measure at 375×667, not only a tall modern-phone screenshot.
- The 404 page has a meaningful Arabic explanation and direct catalogue recovery (`src/pages/404.astro:6–11`). No definite source-level blocker found; verify actual 404 status, phone title wrapping and recovery links in the browser.
- Search matches the full opening half in catalogue even though mobile visually hides that half (`diwan :120`, `:380`). Try a query found only in the hidden second half: consider whether result feedback should identify why a row matched.
